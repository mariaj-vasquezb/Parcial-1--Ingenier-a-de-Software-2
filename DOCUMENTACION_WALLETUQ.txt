WALLETUQ — DOCUMENTACIÓN DEL PROGRAMA Y GUÍA DE USO
Fecha: 28 de septiembre de 2026 · Actualizado: 18 de octubre de 2026 (F-01 a F-06 del plan de requisitos)
Basado en los archivos del proyecto revisados en esta fecha.

1. ¿QUÉ ES Y PARA QUÉ SIRVE?

WalletUQ es un prototipo académico de una billetera digital. Permite crear una cuenta, iniciar sesión con documento y PIN o con la biometría del dispositivo, recargar saldo simulado, transferir a otro usuario, pagar a comercios afiliados con código QR y consultar movimientos. Al transferir o pagar se ganan puntos, que permiten subir de nivel y reducir las comisiones.

Los valores se muestran en pesos colombianos (COP). No se mueve dinero real. Las recargas con tarjeta o cuenta bancaria, la conexión PSE, la verificación de identidad y el envío del SMS con el código de confirmación son simulaciones. La biometría sí usa el sensor real del dispositivo mediante WebAuthn.

2. ¿EN QUÉ ESTÁ HECHO?

El programa tiene tres partes principales:

- Frontend: la interfaz que se ve en el navegador. Está hecha con React y TypeScript. Los archivos .tsx contienen componentes, es decir, partes de la pantalla con su presentación y comportamiento.
- Backend: el servidor que recibe solicitudes, revisa las reglas y guarda las operaciones. Está hecho con Node.js, Express y JavaScript, en archivos .mjs.
- Almacenamiento: un archivo JSON local. No se utiliza MySQL, PostgreSQL ni MongoDB en esta versión.

Para el diseño se usan Tailwind CSS, CSS propio e iconos de Lucide. Vite inicia la interfaz durante el desarrollo y genera la versión compilada.

Flujo general:

Usuario -> interfaz React -> solicitud HTTP con JSON -> API Express
                                                        |
                                                        v
                                            reglas y validaciones
                                                        |
                                                        v
                                            server/data/store.json

La respuesta del servidor vuelve a React y actualiza la pantalla. JSON es un formato de texto para representar objetos y listas. API es el conjunto de rutas por las que la interfaz se comunica con el servidor.

Archivos principales y para qué sirve cada uno:

index.html
Es la página base. Define el idioma español, el título WalletUQ y el elemento root donde React monta la aplicación.

src/main.tsx
Es el punto de entrada del frontend. Carga los estilos y renderiza App dentro de StrictMode, una herramienta de React para detectar problemas durante el desarrollo.

src/App.tsx
Controla si se muestra el acceso o el panel. Si encuentra un token guardado, consulta /api/me para comprobar la sesión. Cierra la sesión (en el servidor y en el navegador) al pulsar salir o tras 15 minutos sin interacción, y muestra el motivo en la pantalla de acceso.

src/Auth.tsx
Contiene las pestañas Ingresar y Registrarme, los campos del formulario y los mensajes de error. Usa las validaciones compartidas y envía los datos a /auth/register o /auth/login. También ofrece Ingresar con biometría. Al autenticarse, guarda el token y muestra el panel. Los errores del registro aparecen al salir de un campo o enviar el formulario y se actualizan al corregirlo.

src/Dashboard.tsx
Contiene el panel con saldo, número de cuenta, puntos, nivel, comisión, límite diario y movimientos recientes, además del botón para activar o desactivar la biometría. También contiene los componentes internos DepositModal (tarjeta o PSE), TransferModal (con el código de confirmación), TransactionRow y Success. Se suscribe a /api/events (Server-Sent Events) y recarga perfil e historial apenas el servidor avisa de un movimiento; cada 15 segundos hace además una consulta de respaldo que no cuenta como actividad.

src/Payments.tsx
Contiene PayModal: lee el QR con la cámara (librería jsQR), desde una imagen subida o pegando el código; pide el monto si el QR no lo trae, muestra comercio, comisión, puntos y total, y confirma el pago. Incluye la lista de QR de los comercios de prueba con opción de descargarlos.

src/biometric.ts
Registra y usa la biometría del dispositivo con @simplewebauthn/browser y traduce las cancelaciones del diálogo del sistema a mensajes en español.

src/Modal.tsx
Es el contenedor reutilizable de las ventanas de recarga y transferencia. Recibe título, contenido y una función para cerrar. Se puede cerrar con la X o al pulsar el fondo.

src/api.ts
Centraliza las solicitudes fetch. Define la dirección http://localhost:4000/api, envía el token en Authorization: Bearer y convierte los errores del servidor en ApiError con su código HTTP. Las consultas automáticas se marcan con la cabecera X-WalletUQ-Background para que no extiendan la sesión. También contiene money y shortDate para dar formato a valores y fechas.

src/types.ts
Define los tipos User y Transaction que usa TypeScript. Los tipos describen la forma de los datos, pero no los almacenan ni sustituyen las validaciones del servidor.

src/styles.css
Define colores, tamaños, tarjetas, formularios, modales y adaptación a pantallas pequeñas. Importa Tailwind y las fuentes DM Sans, Manrope y Playfair Display desde Google Fonts. Las fuentes externas necesitan conexión para descargarse.

shared/registration.mjs
Contiene validateRegistration, usada por frontend y backend para mantener las mismas reglas del registro.

shared/registration.d.mts
Describe los tipos de esa función JavaScript para que TypeScript pueda usarla desde React.

shared/registration.test.mjs
Prueba datos válidos e inválidos y comprueba que un error de correo o documento no se informe como un error del PIN.

server/index.mjs
Crea la API Express. Contiene las rutas de acceso, biometría, registro, perfil, eventos, búsqueda de destinatario, movimientos, recargas, transferencias y pagos QR. Verifica token y sesión y prepara los datos públicos del usuario. Las reglas viven en los módulos siguientes.

server/wallet.mjs
Niveles, comisiones, límites diarios (día calendario de Colombia), puntos, cotización de transferencias y pagos, y referencias únicas. Define WalletError, que lleva el código HTTP de cada rechazo de negocio.

server/kyc.mjs
Proveedor KYC simulado (IF-010). Rechaza los documentos terminados en 0000 para poder probar la validación rechazada.

server/payment-gateway.mjs
Pasarelas simuladas de tarjeta y PSE: valida número (Luhn), vencimiento y CVV; aprueba o rechaza según las tarjetas y el banco de prueba.

server/sessions.mjs
Sesiones del servidor con cierre tras 15 minutos sin actividad.

server/otp.mjs
Código de confirmación de 6 dígitos para transferencias superiores a $1.000.000: vence en 5 minutos, es de un solo uso, admite 3 intentos y solo sirve para el destinatario y monto que se previsualizaron.

server/qr.mjs
Genera y valida el contenido de los QR de comercio (walletuq://pagar?...) firmado con HMAC, para que no se pueda cambiar el comercio ni el monto.

server/merchants.mjs
Comercios afiliados de prueba que se crean automáticamente: Café Universitario UQ (QR con monto fijo de $12.000), Librería Centro Armenia (monto libre) y Minimercado El Norte (inactivo).

server/events.mjs
Mantiene las conexiones Server-Sent Events de cada usuario y les avisa cuando cambia su billetera.

server/webauthn.mjs
Opciones y verificación de WebAuthn con @simplewebauthn/server. Solo se guarda la clave pública; la huella o el rostro nunca salen del dispositivo.

server/store.mjs
Lee y escribe el archivo de datos. Antes de devolver los datos completa las colecciones que falten (archivos de versiones anteriores), crea los comercios de prueba y revisa los bloqueos temporales vencidos. Para guardar, escribe primero un archivo .tmp y luego lo renombra. Incluye resetStore, que vacía todos los datos, pero no está expuesta como una ruta de la API.

server/login-lock.mjs
Define tres intentos como máximo y 15 minutos de bloqueo. Registra fallos, calcula vencimientos, reinicia intentos y genera el mensaje de espera.

server/login-lock.test.mjs
Prueba el tercer intento, el vencimiento exacto del bloqueo, la conservación del plazo y la compatibilidad con bloqueos anteriores.

server/wallet.test.mjs, server/payments.test.mjs y server/security.test.mjs
Prueban niveles y comisiones, límite diario en hora de Colombia, saldo insuficiente, KYC, tarjetas y PSE, QR alterados, inactividad de la sesión, código de confirmación y retos biométricos.

server/smoke-test.mjs
Prueba un flujo completo contra la API de F-01 a F-06: KYC rechazado, documento duplicado, recargas aprobadas y rechazadas, transferencia, pago QR, comercio inactivo, QR alterado y cierre de sesión. Crea datos de prueba en el almacenamiento que utiliza el servidor.

README.md
Contiene el resumen del proyecto, las instrucciones básicas y una lista de requisitos implementados.

package.json y package-lock.json
El primero declara paquetes y comandos. El segundo registra las versiones resueltas y dependencias indirectas para poder reproducir la instalación.

vite.config.ts
Configura los plugins de React y Tailwind para Vite.

tsconfig.json, tsconfig.app.json y tsconfig.node.json
Configuran las comprobaciones de TypeScript. Separan la aplicación y la configuración de Vite. No son archivos de datos de usuarios.

.gitignore
Evita incluir en Git node_modules, dist, .env, archivos de log, información de compilación y server/data/store.json. Por eso los datos locales no viajan automáticamente al clonar el repositorio.

5. ¿DÓNDE ESTÁN LOS REQUISITOS Y LAS REGLAS DEL NEGOCIO?

Un requisito dice qué debe hacer el sistema. Una regla de negocio define las condiciones para hacerlo, por ejemplo cuánto cobrar o cuál es el límite de una transferencia.

No se encontró en los archivos revisados una especificación independiente y completa de los requisitos académicos originales. README.md contiene un resumen; las reglas ejecutables están distribuidas en el código:

- Registro y formato de datos: shared/registration.mjs.
- Documento y correo únicos: server/index.mjs, ruta de registro. Validación de identidad: server/kyc.mjs.
- Tres fallos y 15 minutos de bloqueo: server/login-lock.mjs.
- Cierre de sesión tras 15 minutos de inactividad: server/sessions.mjs y src/App.tsx.
- Biometría: server/webauthn.mjs y src/biometric.ts.
- Niveles, comisiones, límites y puntos: server/wallet.mjs.
- Pasarelas de recarga: server/payment-gateway.mjs.
- Código de confirmación: server/otp.mjs.
- QR y comercios: server/qr.mjs y server/merchants.mjs.
- Presentación de mensajes y formularios: Auth.tsx, Dashboard.tsx y Payments.tsx.

Trazabilidad con el plan de requisitos (Plan_de_Requisitos_WalletUQ.xlsx):

F-01 Registrar usuario          SWR-001  POST /auth/register, kyc.mjs
F-02 Autenticar usuario         SWR-002  /auth/login, /auth/biometric/*, login-lock.mjs, sessions.mjs, webauthn.mjs
F-03 Consultar panel financiero SWR-003  GET /me, GET /events, events.mjs
F-04 Recargar saldo             SWR-004  POST /deposits, payment-gateway.mjs
F-05 Transferir saldo           SWR-005  /transfers/*, wallet.mjs, otp.mjs
F-06 Pagar a comercio por QR    SWR-006  /payments/*, qr.mjs, merchants.mjs, src/Payments.tsx

Los requisitos no se guardan dentro de store.json. Allí se guarda el resultado de usar el sistema: cuentas, saldos, intentos y movimientos.

Reglas del registro:

- Nombre obligatorio y distinto de espacios en blanco. No se exige actualmente un número mínimo de palabras.
- Documento de 6 a 12 dígitos, sin repetirse entre usuarios.
- Correo con dirección y dominio completos, por ejemplo persona@gmail.com. Admite otros proveedores; no está limitado a Gmail. Se guarda sin espacios exteriores y en minúsculas. Debe ser único.
- Celular de 10 dígitos, empezando por 3. No se exige actualmente que sea único.
- PIN de exactamente 6 dígitos. Puede comenzar por cero.
- Confirmación obligatoria de la validación de identidad simulada.
- La cuenta solo se crea si el proveedor KYC aprueba la identidad. En la simulación, un documento terminado en 0000 se rechaza (respuesta 422) y no se crea nada.
- Se valida el formato del correo y celular, pero no se comprueba su existencia ni propiedad mediante mensajes.

Reglas de acceso:

- Se ingresa con documento y PIN o, si se activó en el panel, con documento y la biometría del dispositivo.
- Los fallos se cuentan por cuenta existente. Al tercer PIN incorrecto consecutivo se bloquea durante 15 minutos.
- Ingresar correctamente reinicia los fallos.
- Intentar ingresar durante el bloqueo no alarga su duración.
- El vencimiento se guarda como blockedUntil. Al leer los datos después del vencimiento se activa la cuenta y se reinician los fallos; no hay un temporizador que deba permanecer abierto en el navegador.
- Un bloqueo antiguo por tres fallos, sin fecha, recibe un plazo de 15 minutos la primera vez que lo lee la nueva lógica.
- Cada ingreso abre una sesión en el servidor. La sesión se cierra tras 15 minutos sin actividad del usuario; cada acción la renueva, pero las consultas automáticas del panel no. El navegador también cuenta la inactividad y vuelve a la pantalla de acceso con el motivo. Salir cierra la sesión en el servidor, así que el token deja de servir. El cierre por inactividad y el bloqueo por fallos son mecanismos diferentes.

Niveles y beneficios:

Nivel       Puntos acumulados     Comisión    Límite diario de envío
Bronze      0 a 499               5%          $500.000
Silver      500 a 1.999           3%          $2.000.000
Gold        2.000 a 9.999         1%          $5.000.000
Platinum    Desde 10.000          0%          $20.000.000

Reglas de recarga:

- Mínimo $10.000 y máximo $20.000.000 por operación.
- Sin comisión interna y sin puntos.
- Con tarjeta se valida número (Luhn), vencimiento MM/AA y CVV. 4242 4242 4242 4242 se aprueba y 4000 0000 0000 0002 se rechaza. Solo se guardan los últimos 4 dígitos.
- Con PSE se elige el banco. "Banco de Pruebas (rechaza)" simula un débito rechazado.
- Aprobada o rechazada, la recarga queda registrada con su estado y la respuesta del proveedor. Una rechazada no cambia el saldo. Es una simulación, sin cobro bancario.

Reglas de pago con QR:

- El QR contiene el código del comercio y, opcionalmente, un monto fijo, firmados con HMAC. Un QR alterado o ajeno se rechaza.
- El comercio debe existir y estar activo.
- Si el QR trae monto, se usa ese; si no, el cliente lo escribe.
- La comisión usa las mismas tasas por nivel que las transferencias. El comercio recibe el monto; al cliente se le descuenta monto más comisión, en una sola escritura.
- El cliente gana la parte entera de monto / 10.000 en puntos.

Reglas de transferencia:

- El destinatario debe existir, estar activo y ser diferente del remitente.
- Se identifica por documento o número de cuenta.
- El monto debe ser positivo y el saldo debe cubrir monto más comisión.
- Comisión = monto multiplicado por la tarifa del nivel, redondeada al peso.
- El receptor recibe el monto; al remitente se le descuenta monto más comisión.
- El remitente gana la parte entera de monto / 10.000 en puntos. El receptor no gana puntos por recibir.
- Se aplica el nivel anterior a completar esa operación. Los puntos nuevos pueden mejorar las operaciones posteriores.
- El límite diario suma montos enviados, sin comisiones ni recargas. El día se cuenta en hora de Colombia (America/Bogota).
- Para montos superiores a $1.000.000 se exige un código de 6 dígitos enviado por SMS simulado. Vence en 5 minutos, sirve una sola vez, admite 3 intentos y solo vale para el destinatario y el monto previsualizados. Como no hay proveedor SMS real, el código se muestra en pantalla y en la consola de la API. También deben cumplirse el límite del nivel y el saldo; con los límites actuales, solo desde Silver se puede enviar más de $1.000.000 en un día.
- Ambos saldos, los puntos y el movimiento se modifican en memoria y se guardan con una sola escritura. Si algo falla antes de guardar, ningún saldo cambia.
- El concepto se limita a 80 caracteres.
- Se revisan las reglas en la vista previa y nuevamente al confirmar.

Ejemplo: un usuario Bronze con $200.000 envía $100.000. La comisión es $5.000. Su saldo queda en $95.000, el receptor recibe $100.000 y el remitente gana 10 puntos.

6. ¿DÓNDE SE ALMACENAN LOS DATOS?

El archivo principal es server/data/store.json. Tiene cinco listas:

{
  "users": [],
  "transactions": [],
  "sessions": [],
  "otps": [],
  "merchants": []
}

sessions guarda las sesiones abiertas y su última actividad; otps, los códigos de confirmación pendientes (solo su hash); merchants, los comercios afiliados y lo que han recibido. Un archivo de una versión anterior se completa automáticamente al leerlo.

Si no existe, la lectura parte de listas vacías. El archivo y la carpeta se crean al guardar por primera vez. Los datos continúan allí al cerrar el navegador o reiniciar el servidor.

Cada usuario contiene:

- id: identificador interno UUID.
- document, fullName, email y phone: datos de identificación y contacto.
- accountNumber: número de cuenta generado por el servidor.
- status: estado, normalmente active o blocked.
- failedAttempts: fallos consecutivos del PIN.
- blockedUntil: vencimiento del bloqueo, cuando corresponde.
- pinSalt y pinHash: información para verificar el PIN.
- balance: saldo en pesos.
- points: puntos acumulados.
- kycReference: referencia de la validación de identidad aprobada.
- passkeys: claves públicas de la biometría registrada, cuando se activó.
- createdAt: fecha de creación.

El PIN original no se guarda como texto. Se genera una sal aleatoria y un hash con scrypt. Un hash sirve para comparar el PIN ingresado, no para recuperarlo. El perfil enviado al navegador excluye pinSalt y pinHash.

Nivel, porcentaje de progreso, comisión y límite se calculan a partir de los puntos al preparar el perfil; no son campos persistentes del usuario en esta implementación.

Cada movimiento contiene:

- id y reference: identificador y referencia visible.
- type: deposit, transfer o payment.
- amount: monto principal.
- fee: comisión.
- fromUserId y toUserId: usuario de origen y destino; en recargas el origen es null y en pagos el destino es null.
- merchantCode y merchantName: comercio, en los pagos QR.
- status: completed, o failed para una recarga rechazada.
- failureReason y providerReference: motivo del rechazo y autorización del proveedor, en las recargas.
- description: concepto, origen de la recarga o "Pago con QR".
- createdAt: fecha en formato ISO.

direction y counterpart se calculan al consultar el historial, según quién lo está viendo. La API devuelve los últimos 50 movimientos del usuario; el panel presenta los primeros 6.

En el navegador se guarda el JWT en localStorage con la clave walletuq_token. No es una copia de la base de datos. Cada origen tiene su propio localStorage; por eso los puertos 5173 y 5174 permiten mantener dos cuentas abiertas a la vez.

Editar store.json manualmente cambia la información del sistema. Para conservar los datos de una demostración, se puede hacer una copia del archivo con el servidor detenido. No hace falta modificarlo para registrar, recargar ni transferir desde la aplicación.

7. RUTAS DE LA API

Todas parten de http://localhost:4000/api.

GET    /health                     Comprueba si el servidor responde.
POST   /auth/register              Valida, consulta el KYC y crea una cuenta; devuelve usuario y token.
POST   /auth/login                 Verifica documento y PIN; devuelve usuario y token.
POST   /auth/biometric/options     Prepara el reto biométrico para un documento.
POST   /auth/biometric/verify      Verifica la biometría; devuelve usuario y token.
POST   /auth/logout                Cierra la sesión en el servidor.
POST   /session/ping               Informa actividad del usuario sin otra operación.
POST   /biometric/register/options Prepara el registro de la biometría.
POST   /biometric/register/verify  Guarda la clave pública de la biometría.
DELETE /biometric                  Desactiva la biometría.
GET    /me                         Devuelve el perfil de la sesión.
GET    /events?token=...           Canal Server-Sent Events con avisos de cambios.
GET    /users/lookup?q=...         Busca otro usuario por documento o cuenta.
GET    /transactions               Devuelve el historial del usuario.
GET    /deposits/banks             Lista los bancos PSE.
POST   /deposits                   Procesa una recarga con tarjeta o PSE.
POST   /transfers/preview          Calcula destinatario, comisión, total, puntos y si requiere código.
POST   /transfers/otp              Envía el código de confirmación por SMS simulado.
POST   /transfers                  Confirma el envío y guarda saldos y movimiento.
GET    /merchants                  Lista los comercios de prueba con el contenido de su QR.
POST   /payments/preview           Valida el QR y el comercio; calcula comisión, total y puntos.
POST   /payments                   Confirma el pago QR.

Las rutas desde /auth/logout necesitan una sesión válida (salvo /events, que recibe el token en la consulta porque EventSource no admite cabeceras). La búsqueda /users/lookup existe en el backend, pero el formulario de transferencia actual obtiene los datos del destinatario mediante la vista previa.

Respuestas frecuentes: 400 para datos inválidos o código incorrecto, 401 para credenciales o sesión inválidas o cerradas por inactividad, 402 para recarga rechazada por el proveedor, 403 para cuenta no disponible, 404 para destinatario o comercio no encontrado, 409 para documento o correo repetido o comercio inactivo, 422 para KYC rechazado y 423 para cuenta bloqueada.

8. CÓMO INSTALAR Y EJECUTAR

Se necesita Node.js y npm. Según los requisitos de las dependencias fijadas en esta copia, usa Node.js 22.12 o superior compatible. Comprueba la instalación con:

node --version
npm --version

En PowerShell, abre la carpeta:

cd "C:\Users\MARIA JOSE\Desktop\wallet"

Instala las dependencias respetando el archivo de versiones:

npm ci

El README también permite npm install. npm ci reproduce la instalación desde package-lock.json; npm install puede actualizar ese archivo según las dependencias declaradas.

Inicia todo:

npm run dev

Este comando abre tres procesos en la terminal:

- Backend: http://localhost:4000
- Cliente A: http://localhost:5173
- Cliente B: http://localhost:5174

Abre las direcciones de los clientes en dos pestañas. Mantén la terminal abierta mientras usas el programa. Ctrl+C detiene los procesos iniciados por este comando.

También se pueden ejecutar por separado, en terminales distintas:

npm run dev:api
npm run dev:a
npm run dev:b

Vite actualiza la interfaz al guardar cambios. El backend se ejecuta con node, sin modo watch, por lo que los cambios del servidor requieren reiniciarlo.

Configuración:

- PORT cambia el puerto del backend; por defecto es 4000.
- JWT_SECRET permite configurar la clave de firma; hay una clave de desarrollo como valor por defecto.
- QR_SECRET firma los QR de los comercios; también tiene un valor de desarrollo. Si cambia, los QR ya descargados dejan de ser válidos.
- WEBAUTHN_RP_ID es el dominio de la biometría; por defecto localhost. Abre la aplicación como localhost (no 127.0.0.1) para que la biometría funcione.
- La aplicación no incluye carga automática de .env. Las variables deben suministrarse al proceso, por ejemplo mediante variables de entorno de PowerShell.
- Si cambias el puerto de la API, actualiza API_URL en src/api.ts.
- CORS permite actualmente los clientes http://localhost:5173 y http://localhost:5174.

9. CÓMO USAR LA APLICACIÓN

Crear una cuenta:

1) Abre el cliente A y selecciona Registrarme.
2) Ingresa nombre, documento, correo completo, celular y PIN.
3) Marca la confirmación de identidad simulada.
4) Pulsa Crear mi cuenta. Si los datos son válidos, únicos y el KYC los aprueba, entrarás al panel con saldo y puntos en cero. Para ver un KYC rechazado, usa un documento terminado en 0000.

Ingresar después:

1) Selecciona Ingresar.
2) Escribe el documento y PIN de la cuenta creada.
3) Pulsa Entrar a mi billetera.
4) Si se bloquea por tres PIN incorrectos, espera el plazo indicado antes de volver a intentar.

Ingresar con biometría:

1) En el panel, pulsa Activar biometría y confirma con la huella, el rostro o el método del dispositivo.
2) Después de salir, escribe solo el documento y pulsa Ingresar con biometría.

Recargar:

1) Pulsa Recargar.
2) Escribe el monto, sin puntos ni símbolos; por ejemplo 200000.
3) Con tarjeta, escribe 4242 4242 4242 4242, un vencimiento futuro y un CVV de 3 dígitos. Con cuenta bancaria, elige el banco PSE.
4) Confirma. El panel muestra el saldo y el movimiento. Una recarga rechazada aparece tachada en el historial y no cambia el saldo.

Pagar con QR:

1) Pulsa Pagar y permite el uso de la cámara.
2) Apunta al QR del comercio. También puedes subir una imagen del QR o pegar su código.
3) Para probar sin otro dispositivo, pulsa Ver QR de comercios de prueba: allí puedes descargarlos o pagar directamente.
4) Si el QR no trae monto, escríbelo. Revisa comisión, puntos y total, y pulsa Confirmar pago.

Transferir y demostrar dos usuarios:

1) Crea otra cuenta en el cliente B con documento y correo diferentes.
2) Copia su documento o su número de cuenta del panel.
3) En el cliente A, con saldo disponible, pulsa Transferir.
4) Ingresa el destinatario, el monto y un concepto opcional.
5) Pulsa Continuar y revisa quién recibe, la comisión y el total.
6) Si el monto supera $1.000.000, escribe el código que aparece en el SMS simulado.
7) Confirma el envío.
8) Revisa ambos clientes. El receptor ve el cambio de inmediato (menos de 2 segundos).

Para repetir el ejemplo de la sección 5, usa dos cuentas nuevas, recarga 200000 en A y transfiere 100000 a B. Así los saldos iniciales y el nivel coinciden con el ejemplo.

Otras acciones funcionales:

- El icono del ojo muestra u oculta el saldo.
- El icono de copiar copia el número de cuenta.
- El botón de salida, junto al usuario en la barra lateral, cierra la sesión de ese cliente.
- En pantallas pequeñas, el botón de menú abre la barra lateral.

10. QUÉ FUNCIONA Y QUÉ ESTÁ PENDIENTE

Funcionan F-01 a F-06 del plan de requisitos: registro con KYC, acceso con PIN o biometría, bloqueo temporal, cierre por inactividad, panel en tiempo real, recargas con tarjeta o PSE (aprobadas y rechazadas), transferencia con código de confirmación, pago QR, puntos e historial reciente.

Los botones Movimientos, Mis cuentas, Recompensas, Mi nivel, Ver todos y notificaciones no tienen actualmente un flujo completo conectado (corresponden a funcionalidades posteriores del plan, como F-07 a F-15). El buscador superior no filtra movimientos. Que estos elementos aparezcan en pantalla no significa que esas funciones estén implementadas.

No hay recuperación del PIN, verificación real por correo, proveedor SMS real ni conexión bancaria. El KYC y las pasarelas son simulaciones con datos de prueba. El texto Cuenta verificada se presenta como parte de la demostración.

El guardado usa un archivo local y operaciones síncronas. Una transferencia modifica ambos saldos y agrega el movimiento antes de guardar el conjunto. Esto resulta adecuado para la demostración con un servidor, pero no equivale a las transacciones y controles de concurrencia de una base de datos para varias instancias.

13. PROBLEMAS FRECUENTES

No conecta con el servidor:
Comprueba que npm run dev o npm run dev:api esté activo y que http://localhost:4000/api/health responda. La interfaz y el backend son procesos distintos.

Puerto ocupado:
Los clientes usan strictPort y no eligen otro automáticamente. Detén la instancia anterior o revisa la configuración de puertos y CORS.

No aparecen los cambios del backend:
Detén y vuelve a iniciar el servidor. Guardar el archivo no reinicia el proceso actual.

Correo o documento ya registrado:
La cuenta ya existe en los datos locales. Inicia sesión con ella o utiliza datos distintos para la demostración.

Saldo insuficiente:
La transferencia descuenta monto más comisión. Recarga lo necesario y revisa el total de la vista previa.

Límite diario superado:
Se suman las transferencias realizadas en el día (hora de Colombia). Recargar más dinero no aumenta el límite del nivel.

La cámara no abre en Pagar:
El navegador necesita permiso de cámara y solo lo concede en localhost o HTTPS. Si no hay cámara, sube una imagen del QR o usa Ver QR de comercios de prueba.

No aparece Ingresar con biometría o falla:
El navegador debe soportar WebAuthn y la aplicación debe abrirse como localhost. Primero hay que activarla desde el panel en ese mismo dispositivo.

No aparecen los datos después de copiar el proyecto:
store.json está excluido de Git. Una copia del código sin ese archivo comienza sin las cuentas locales.

Cuenta bloqueada:
Espera el tiempo del mensaje. La fecha queda guardada en el servidor; cerrar la pestaña o reiniciar la API no elimina el plazo.
